## RCA

### P-01：同じ種類の指摘が 3 回続いた

- なぜ 1：Codex が、成分の比が極端な入力、打ち消し合う和、ほぼ平行なベクトル、非正規化数を入れるたびに、N-08 の条件が破れた。
- なぜ 2：テストの格子は「ベクトル全体の大きさ × 向き × 特別な値」で、成分ごとに独立に値を変える組、打ち消し合う和、ほぼ平行（隣の浮動小数点数へずらす）、非正規化数を含んでいなかった。条件の文も「一致する」「向き」と書き、浮動小数点数でどこまで守れるか（誤差の上限、最小の刻み）を書いていなかった。
- なぜ 3：前回の T-02 で決めた手順（README の「開発の進め方」）は、格子を「大きさ × 向き × 特別な値」とだけ書き、悪条件の入力（打ち消し合い、ほぼ平行、非正規化数）と、条件の精度（誤差の上限と、それが守れる理由）を求めていなかった。期待値の求め方（正確な参照値と比べる）も決めていなかった。
- 根本原因：数値の関数の出力の条件を、浮動小数点数で守れる精度（誤差の上限、最小の刻み）つきで書く手順と、成分ごとの値と悪条件の入力を含む格子を正確な参照値と比べる手順がない。
- 再発防止策：
  - 出力の条件は、「一致する」ではなく誤差の上限（最小の刻み 2⁻¹⁰⁷⁴ を含めて）で書き、守れる理由を添える。符号や向きのように正確さが要る条件は、整数（BigInt など）で正確に計算する（README の「開発の進め方」、作業の決まり）。
  - テストの格子は、成分ごとに独立に値（±極大、1、極小、非正規化数、0）を入れ、打ち消し合う和、ほぼ平行、非正規化数を含める。期待値は、整数で正確に求めた参照値と比べるか、参照値自身の誤差を上限から引いた幅で比べる（同上）。

### P-02：CI の失敗にマージの直前まで気づかなかった

- なぜ 1：push のあと、PR の CI の結果を見ていなかった。
- なぜ 2：手元で同じ検査（cargo、npm、e2e、Lighthouse）を実行して通っていたので、CI も通ると考えていた。手元の検査には、CI の最初の段階の `npm audit` が入っていなかった。
- なぜ 3：CI を確かめる手順は「セッションの始め」と「マージの前」だけで、レビューと修正をくり返す途中（push のたび）にはなかった。
- 根本原因：push のたびに、そのコミットの CI の結果を確かめる手順がない。
- 再発防止策：push のあと、そのコミットの CI の run を `headSha` で特定して終わるまで待ち、結果を確かめてから、返信や次のレビューに進む（作業の決まり、skill `codex-review` の手順 5）。`gh pr checks --watch` は push の直後だと前の run を見て終わることがあった（この PR で 1 回）。
